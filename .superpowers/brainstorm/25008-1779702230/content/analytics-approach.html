Analytics Pipeline — Architecture

Three approaches, different tradeoffs

A

Recommended — Integrated + Async

Redirection service records clicks to a clicks table fire-and-forget (doesn't block redirect). API service queries aggregated stats. Uses ua-parser-js + free GeoIP. Simple, no new services.

Pros

  • No new microservice
  • Leverages existing DB
  • Fast redirects

Cons

  • More write load on PG
  • GeoIP adds latency
B

Event-Driven (Redis Streams)

Redirection service publishes click events to a Redis stream. A separate consumer processes batches (parse UA, geo, deduplicate) and writes to DB.

Pros

  • Redirects never blocked
  • Batch processing efficient
  • Resilient to consumer failure

Cons

  • New consumer service
  • Redis stream management
  • Eventual consistency
C

Dedicated Analytics Service

New Hono service that receives click events via HTTP, processes them, and serves aggregated stats via API. Cleanest separation.

Pros

  • Clean separation
  • Can scale independently
  • Clear API boundary

Cons

  • Another Docker service
  • HTTP overhead per click
  • More to maintain
